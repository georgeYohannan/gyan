- 2026-11-16: Quiet body text color is #94A3B8. It is not in CLAUDE.md. It was chosen because it keeps 4.5:1 contrast on the navy background.

- 2026-11-16: Added status text colors that are not in CLAUDE.md: green #86EFAC (Ready) and soft red #FCA5A5 (Failed and errors). Both pass 4.5:1 on navy. White text on the orange record button (#C2410C) also passes 4.5:1. Brand blue is still never used as text.
- 2026-11-16: The help panel is a side panel on web windows 768 points wide or more, and slides up from the bottom on phones and narrow windows. All help words live in src/content/help.ts.
- 2026-11-16: /design is a builders-only page. On web it has a route but no tab button. On phones it is a "Design" tab that only appears in development builds (__DEV__), never in store builds.
- 2026-11-16: Google sign in is NOT in this step. Version 1 starts with email and password. Google needs a Google Cloud project and separate keys for web, iPhone, and Android, so it comes in its own later step. The product spec still lists it for version 1.
- 2026-11-16: The chunks table (search pieces of transcript) is not created yet. It needs a vector size, which depends on the embedding model, and that is still an open decision.
- 2026-11-16: The private file storage bucket and its rules are not created yet. No file upload exists yet. They come with the Upload feature.
- 2026-11-16: Row Level Security: the app can read only; server functions write. Members can read invites. Only owners read integrations (they may hold tokens). The app can change only display_name and preferred_language on a profile, so is_admin can never be changed from the app.
- 2026-11-16: Sign up trigger (public.handle_new_user) makes the profile, a Free-plan account, and the owner row in one step, and looks the plan up by name from the plans table. Passwords need at least 8 characters.
- 2026-11-16: The first-sign-in consent note is remembered per person on that device (not in the database). The wording needs a lawyer's review before public launch.
- 2026-11-16: The Design tab is removed from phones. The /design page still exists as a builders-only page you can open by typing its address on web. This replaces the earlier decision to show a Design tab in development builds.
- 2026-11-16: Upload size is capped at 50 MB per file, the Supabase Free plan limit (checked in the current docs). Founder chose to take the audio out of videos before upload instead of upgrading. This is built for the web (decoded in the browser, saved as a 16 kHz mono MP3 at 32 kbps, about 14 MB per hour). On phones it is not built yet: videos up to 50 MB upload as they are, bigger ones are refused with a friendly message. Phone extraction needs a native library and a development build.
- 2026-11-16: The MP3 maker is @breezystack/lamejs, which has an LGPL license. A lawyer should confirm it is fine for the paid product before public launch.
- 2026-11-16: The app still cannot write to the meetings table. It uses 4 database functions: create_note, mark_note_queued, mark_note_failed, restart_note_upload. They check the person belongs to the account. create_note refuses uploads when the plan limit is reached (limit read from the plans table). Files go in the private bucket notes-files at account id / note id / file name.
- 2026-11-16: Pasted text and uploaded text files are saved as source "text". They never count toward the monthly limit, so they are allowed even when the limit is reached. At the limit, Upload is blocked and Paste text still works. Notes count only when Ready (a later step).
- 2026-11-16: New note is opened from the Home button. It has no tab button of its own.
- 2026-11-16: Help entries can now have short lists under the sentences (used for statuses, file types, and the limit).
- 2026-11-17: Deepgram settings: model nova-3, diarize_model=latest (speaker labels; the old diarize=true is deprecated), detect_language=true, utterances=true, smart_format=true. The audio goes to Deepgram as a 10 minute private link, not as bytes through our function. Speakers are saved as "Speaker 1", "Speaker 2".
- 2026-11-17: Deepgram cost in ai_usage uses $0.0052 per minute (Nova-3 multilingual, the higher price, from deepgram.com/pricing). Speaker labels cost nothing extra. The rate is in supabase/functions/transcribe/settings.ts. It is a vendor cost, not a plan price, so it is not in the plans table.
- 2026-11-17: The Deepgram key is the server secret DEEPGRAM_API_KEY (set with supabase secrets set). In .env.local it is named EXPO_DEEPGRAM_KEY, only so you can copy it into the secret. The app never reads it.
- 2026-11-17: 3 server-only database functions (claim_transcription, finish_transcription, fail_transcription) do the status changes. Only the server key can run them. "Ready" and the +1 to the monthly count happen in one database step with the ai_usage row. A failed note never counts. Retry of a Failed note is allowed (it checks the plan limit again).
- 2026-11-17: Supabase Free server functions stop after 150 seconds, so very long recordings (about an hour or more) may end as Failed. Later options: Deepgram's callback option, or a paid Supabase plan. A note can also stay on Transcribing if the server stops halfway. An automatic rescue is not built yet.
- 2026-11-17: Pasted text and text files have no audio, so they get no transcript step. Note pages open from the Home list at /note/<id> and have no tab button.
- 2026-11-17: The current Supabase project stays the TEST project for good. For going live, the founder will set up a NEW paid Supabase project (new keys, new secrets, migrations and functions pushed again). Nothing live shares data with the test project.
- 2026-11-17: Screens opened from Home (New note, a note page) now live in a Stack inside the Home tab (src/app/(app)/(home)/). They were "hidden tabs" before, which Expo says cannot be navigated to, so on iPhone the New note screen flashed and bounced back. Web addresses are unchanged (/, /new-note, /note/<id>).
- 2026-11-18: The summary and action items are written by Claude Sonnet 5.5. It was chosen because it is good at meeting notes, it can be forced to answer in a strict shape (so the app always gets readable data), and it costs about half of the Opus model. About 4 to 6 cents for a 1 hour meeting ($2 per million tokens in, $10 per million out, checked 2026-11-17). The model name, the thinking effort ('low'), and the prices live in supabase/functions/summarize/settings.ts. To change model, change that one line.
- 2026-11-18: Anthropic's Workload Identity Federation (short-lived tokens instead of an API key) cannot be used with Supabase server functions today. Federation needs the workload to get a signed OIDC token from a provider it runs (AWS, Google Cloud, Azure, Kubernetes, GitHub Actions, SPIFFE or Okta). Supabase gives functions no such token and publishes no signing keys for them. So Gyan uses an API key kept as the Supabase server secret ANTHROPIC_API_KEY. Revisit federation before public launch. Keep a separate key for test and for live, and set a monthly spend limit in the Claude Console.
- 2026-11-18: A meeting now counts (+1 for the month) only when the note becomes Ready, not when the transcript finishes. Two new columns on meetings do this: counted_at (stamped the first time it counts, so Regenerate never counts twice) and summary_started_at (a lock, so two taps cannot pay for two summaries, and a stuck note can be picked up again after 3 minutes). A note that fails at any step never counts.
- 2026-11-18: The monthly meeting limit counts every source the same way: 1 uploaded recording, 1 phone recording, or 1 bot meeting each count as 1. Pasted text and uploaded text files never count, and they still work when the limit is reached. This confirms the "Confirm" row in docs/product-spec.md.
- 2026-11-18: Recap emails go to whoever the account owner picks: the owner only, the team members, or both. The default is the owner only, so nobody is emailed without the owner deciding it. The choice is saved per account in the integrations table and can be changed at any time. (The email feature itself is a later step.)
- 2026-11-18: The meeting bot is built behind a feature switch that stays OFF until a lawyer has reviewed the consent wording. Nobody can send a bot to a call until the switch is turned on. This matches the rule that Gyan never records or joins a meeting without a clear consent notice.
- 2026-11-18: If a transcript were ever too long for one request, the note fails with a plain message and no text is ever cut off quietly. Chunking is NOT built, because Claude Sonnet 5.5 holds about 1,000,000 tokens (roughly 100 hours of talking) and no realistic meeting comes close. The guard is MAX_INPUT_TOKENS in supabase/functions/summarize/settings.ts. If it is ever needed, the plan is: split the transcript at speaker turns into parts of about 20 minutes, summarize each part, then summarize the summaries into one, and log every call in ai_usage.
- 2026-11-18: A bad answer from the AI is tried exactly once more, then the note fails with a plain message. Both tries are paid for, so both are added into the one ai_usage cost row.
- 2026-11-18: Browser test scripts live in tests/ and are run with `npm run e2e` (@playwright/test). They answer every Supabase and AI call with fake data (tests/fixtures/fake-api.ts), so they cost nothing, need no account, and never touch real data. They check the interface, not the real services. The real end to end check, with the real AI, is the hand checklist in docs/testing/prompt-6.md. The scripts start the web app with `expo start --web --clear`, because a bundle left over from before new files were added gives a "Requiring unknown module" error.
- 2026-11-18: The side chat answers **all at once**, not word by word. Founder's choice: a streamed answer is nicer to watch but is more code and one more thing to break, and the whole answer arrives in 5 to 10 seconds anyway. The `chat` server function waits for Claude and returns the finished answer in one reply, well inside Supabase's 150 second limit. If streaming is wanted later, it is a change to 1 function and 1 panel.
- 2026-11-18: On a wide web window the chat **floats over** the note from the right, exactly like the help panel. Founder's choice: it reuses a pattern that already works instead of rebuilding the page as 2 columns. Tapping a passage number closes the chat so the highlighted transcript line is in plain view. On a phone it slides up from the bottom. The chat is drawn as a pop-up layer (a Modal), not as a box inside the page, because the bar at the top of the web app is drawn over anything inside the page.
- 2026-11-18: The side chat sends the **whole transcript as numbered passages**, not the closest pieces found by a search. docs/data-model.md describes the search version, which needs the `chunks` table and an embedding model. Neither exists, and for a chat about 1 note the search is not needed: a 1 hour meeting is a small fraction of what the model can hold. Passage 1 is the first transcript line, passage 2 the second, and so on. The embedding decision stays open for the all-notes chat and the Search screen.
- 2026-11-18: The daily chat limit is a column on the plans table, `chat_messages_per_day`, one number per plan, so it is set by the subscription and an admin can change it with no new code. The Free plan starts at 20 questions a day (about 15 cents a day per person at worst). The day starts at midnight UTC, the same as the monthly meeting count. Never hard code this number.
- 2026-11-18: A chat is **more private than a note**. Notes are shared with everyone on the account, but a chat can only ever be read by the person who asked. This narrows the earlier rule (any account member could read any thread). It is done in `private.can_read_thread` and the "Read own chat threads" rule.
- 2026-11-18: A question is saved before the answer is asked for, and the daily limit is checked in the same database step, so two fast taps can never slip past the limit. If the answer then goes wrong, **Retry re-uses the question that is already saved** (`claim_chat_retry`), so a problem never costs somebody a second question out of their day.
- 2026-11-18: The chat has its own settings file, `supabase/functions/chat/settings.ts`, separate from the summary's. It starts on the same model (Claude Sonnet 5.5) and the same 'low' thinking effort, because answering from passages that are right in front of the model is reading work. Keeping it separate means the chat can be tuned or moved to another model without touching summaries. The transcript is marked as worth remembering between questions (prompt caching), so follow-up questions about the same note cost about a tenth as much to read it again.
- 2026-11-18: Chat answers must cite a passage number for each fact, and must say "I could not find that in your notes." when the answer is not there. A number that points at no real line is dropped before it reaches the screen, so a link can never be dead.
- 2026-11-18: Screens that are not built yet are **drafted in Sleek** (sleek.design) before they are coded, starting with Search, Settings, Plan and billing, and Team. The drafts are pictures only: Sleek writes web code, so every screen is rebuilt by hand with the pieces in `src/components/ui`. The brief sent to Sleek pins our own colours, fonts and component rules so the drafts cannot drift into a different look, and the numbers, names and prices in them are stand-ins (real limits and prices always come from the `plans` table). The free account holds **1 project**, so all drafts live in one project: https://sleek.design/project/tWmySNLIkTd. The key is `SLEEK_API_KEY` in `.env.local`, a build-time design tool only; the app never reads it and it is never shipped. Beyond the free trial credits, more design runs need Sleek's Pro plan at $49 a month, or $30 a month billed yearly.
- 2026-11-18: Pasted text and uploaded text files can be asked about too, not just recordings. They have no transcript, so their words are cut into numbered paragraphs instead: blocks separated by a blank line, or one per line when there are no blank lines. The Transcript tab shows them as "Paragraph 1", "Paragraph 2" (it used to say "No transcript lines" and was a dead tab), and a number in an answer jumps to a paragraph the same way it jumps to a spoken line. The cutting happens in 2 places, `src/lib/passages.ts` for the screen and `supabase/functions/chat/chat.ts` for the AI, and `__tests__/passages-test.ts` proves the 2 copies cut text identically. If they ever drifted, a number would point at the wrong paragraph.
- 2026-11-18: Translation runs on **Claude Sonnet 5.5**, the same model as summaries and the chat. Founder's choice: one model to keep track of, and the strongest of the cheap models on Hindi, Arabic and Japanese, which are the scripts Gyan is tested with. Claude Haiku 5.5 would be about 20 times cheaper for the same job if cost ever becomes the problem. The model, the thinking effort ('low'), the prices and the length limit live in `supabase/functions/translate/settings.ts`, separate from the summary's and the chat's, so translation can be tuned on its own.
- 2026-11-18: A long transcript is **refused with a plain message, not cut short and not split**. Founder's choice between one request with a cut-off and splitting the work into parallel batches. `MAX_TRANSCRIPT_TOKENS` is 6,000, about 30 minutes of English talking, because one Supabase server call is stopped after 150 seconds. Hindi, Arabic and Japanese need noticeably more room than English for the same meaning, so the real cut-off is lower for those. Summaries are always small and are never affected. If longer notes are needed, the plan is to cut the transcript at speaker turns into batches of about 60 lines, translate them at the same time, join them in order, and log every batch into the one ai_usage row. That is a change to `pipeline.ts` only.
- 2026-11-18: `translations` and `profiles.preferred_language` already existed from the first two migrations, and the side chat already answered in `preferred_language`. The only thing missing was a server-only way to WRITE a translation, so the new migration adds just 2 functions (`claim_translation`, `save_translation`) and changes no existing rule. The app can still only read translations.
- 2026-11-18: The Summary tab is translated as **one saved piece** (overview, key points, decisions, open questions and the to-dos together), saved under kind `summary` with the summary's id. docs/data-model.md lists a separate `action_items` kind; it stays unused for now. One piece means one lookup, one AI call and one cost row, and the to-dos can never line up against the wrong tick boxes. The `action_items` kind is still there if it is ever wanted.
- 2026-11-18: Only **words** are sent to be translated, never an id, a speaker label or a time. What comes back is lined up with the original **by position**, so a list that comes back a different length is treated as a bad answer and asked for once more, then the note fails with a plain message. Both tries are paid for and go into the one ai_usage row, the same rule as the summary.
- 2026-11-18: No prompt caching for translation. The chat caches its transcript because the same note is read again and again; a translation is paid for once and then saved for good, so there is nothing to cache. This also keeps the prompt in the order docs/data-model.md writes it.
- 2026-11-18: **Font fallbacks for other scripts.** Schibsted Grotesk is Latin only and IBM Plex Sans covers Latin, Cyrillic and Greek, so Spanish, French and Russian were already fine. Arabic and Hindi now load `@expo-google-fonts/ibm-plex-sans-arabic` and `-devanagari` (Regular and SemiBold only): same type family, same look, SIL Open Font License, small. **Japanese, Chinese and Korean use the device's own font**, because `@expo-google-fonts/ibm-plex-sans-jp` is a 17 MB package, far too big to ship for one language. Every phone and browser already has a font for those scripts, so the words are correct and readable, just not in Plex. The choice is one line per language in `src/constants/languages.ts`.
- 2026-11-18: **Right to left is done per block, not for the whole app.** Only the translated words turn around; the buttons, tabs and headings stay in English on the left. `writingDirection` is an iPhone-only setting (checked in the current React Native docs), and on the web a Text does not inherit the browser's automatic direction when it sits inside another Text, so `src/components/ui/script-text.tsx` right-aligns on every platform, sets `writingDirection` on iPhones, and says `dir` out loud on the web. Checked by screenshot: Arabic reads right to left with its letters joined up, next to English speaker names and times. A full right-to-left app is not in version 1.
- 2026-11-18: The paragraph-cutting code now exists in **3** places, not 2: the app, the chat function and the translate function. `__tests__/passages-test.ts` compares all three on the same samples, so they cannot drift. Supabase deploys each function folder on its own, so sharing one copy across folders was not worth the deploy risk.
- 2026-11-18: There is **no limit on how many translations** a person may ask for. Each one is bought once and kept, so the worst case is about $2.40 for one long note in all 16 languages. If a limit is ever wanted it would be a `translations_per_day` column on the plans table, like `chat_messages_per_day`.
- 2026-11-18: The translating rules were too soft and left ordinary English words inside translated sentences ("ledger", "workpapers", "chain of custody", "frontend", "persona"). The rule "If a word has no good translation, keep the original word" was the licence for it, and it is gone. The rules now say to translate every ordinary word including technical, legal, financial and business ones, name exactly what may stay in English (people's names, company, product and brand names, file names, code, web addresses, numbers, dates, times, speaker labels, timestamps), and end with the test that matters: somebody who reads the target language and no English at all must understand every sentence. Changed in docs/data-model.md and in supabase/functions/translate/translate.ts together.
- 2026-11-18: Translated words are saved with the **version of the rules that made them** (`"v"` inside the saved content), and a translation saved under an older version is made again the next time somebody asks for it. Without this, a change to the translating rules could never reach a note that had already been translated, because a translation is only ever bought once. It costs one re-translation per note and language, once, and then it is free again. The number lives in 3 places (the server, the app, and the browser scripts, which cannot import app code) and a test keeps them in step. It is deliberately NOT a database column: the content column is free-form, so no migration and no signature change were needed.
- 2026-11-18: The preferred language is set from the **Your account box at the bottom of Home**, not only from the note page. The founder could not find it on the note page, which is fair: nobody looks for their own settings inside a note. The note page keeps its Language button because it is handy there. Both open the same picker. The whole thing moves to the real Settings screen in prompt 10.
- 2026-11-18: The new translation screens were put through the **frontend-design** skill, which CLAUDE.md asks for on any visual work and which was skipped the first time round. Four things changed, all about information rather than decoration. (1) The "Spanish · Translated by AI" bar used a middle-dot meta string, which that skill names as one of the commonest tells of generated design; it is now two lines, "Translated by AI" over "Spanish. Names, numbers and times are unchanged." (2) Language, Translate and Ask were three identical pills, but Language only shows a setting while the other two act on the note; Language is now quiet (grey border, quiet text) and the two actions keep the brand blue. (3) In the language list, the language you are on and the row your finger is on looked the same; the chosen one now has a brand-blue outline and a press is only a fill. (4) The Your account box stacked a quiet label above every value; it now leads with the value and puts the explanation under it, which is how a settings row is normally built. Checked by screenshot at 390 and 1280.
- 2026-11-19: Recap emails are sent from **gyan <hello@gyantechai.com>**, with hello@gyantechai.com as the reply address too. Both live in ONE place, `SENDER` in `supabase/functions/recap/settings.ts`, so the address is never written into the code that builds an email (a test proves `email.ts` holds no copy of it). The root domain gyantechai.com was already verified with Resend before this step: the live DNS already had the MX and SPF records on `send.gyantechai.com` and the DKIM key on `resend._domainkey.gyantechai.com`. None of those touch the Hostinger mailbox on gyantechai.com itself, because they sit at different names, so **no DNS record was added, changed or deleted for this feature**. A separate sending subdomain (for example mail.gyantechai.com) is what Resend recommends in general, because it keeps the product's sending reputation apart from the founder's own mailbox; the founder chose hello@gyantechai.com for now, and moving later is one line in that settings file plus 3 new DNS records.
- 2026-11-19: **A recap can never reach anybody outside the account, and an email address is never an input.** The app sends a list of user ids, not addresses. The addresses themselves exist only inside `claim_recap`, which reads them from `account_members` joined to `auth.users`. An id that is not on the account is dropped silently. This is why the Send recap dialog shows addresses but never lets anybody type one.
- 2026-11-19: Recap settings live on the existing `integrations` table as `kind = 'recap_email'`, with `settings` `{ to_owner, to_members, auto_send }`, which is what docs/decisions.md 2026-11-18 said they would. The only change to that table is a unique index on (account_id, kind), so saving overwrites cleanly. Its rules were already owner-only, so no rule was changed. Defaults when no row exists: the owner only, and **the automatic send OFF**. Nobody is emailed until the owner decides it.
- 2026-11-19: A team member can **read** the recap settings but not change them. The `integrations` table stays owner-only to read (it may one day hold Slack and Teams tokens), so a small app-callable door, `get_recap_settings()`, hands back only the three switches plus whether the caller is the owner. `save_recap_settings(jsonb)` is owner-only and **raises an error out loud** rather than silently changing nothing, so the screen can say why. Any member may press Send recap on a note they can already read; sharing a note is not a settings change.
- 2026-11-19: Everybody gets the recap **in their own language**, and a language nobody has translated into yet is bought (founder's choice over "saved translations only"). Two guards go with that choice, because an automatic send spends money with nobody pressing anything: `MAX_TRANSLATIONS_PER_SEND` in `supabase/functions/recap/settings.ts` (5), and a fall back to the original language whenever a translation fails, is refused, or is past the ceiling. An email always goes out; a translation problem never swallows a recap. Two people who read the same language share one translation.
- 2026-11-19: The recap function **reuses the translate function** rather than growing a second copy of the translating rules. To do that, `translate/index.ts` gained a trusted-internal door: when the Authorization bearer is the project's own secret key (which only our own server code holds), it takes a `user_id` from the body instead of from a login. This does not widen anything — `claim_translation` still checks in SQL that that person is on the note's account — and the translation is saved in the usual place, so the next person who wants that language gets it free. `recap/index.ts` has the same door, for the automatic send.
- 2026-11-19: The automatic send is **chained off the summarize function**, not a database trigger. `finish_summary` is the only place a note becomes Ready, so `runSummary` now takes an injected `onReady`, and `summarize/index.ts` uses it to call the recap function inside the existing `EdgeRuntime.waitUntil` work. Injecting it keeps the summary tests network-free. A failure inside `onReady` is written down and swallowed, so an email problem can never undo a note that is already Ready, and a note that fails never emails anybody. `claim_recap` refuses a second automatic send for the same note, so Regenerate cannot email everybody twice.
- 2026-11-19: For the automatic send there is no person behind the request, so `claim_recap` takes an empty `p_user_id` when `p_auto` is true and lets the account's settings decide alone. That is safe because the function is service_role only (the app can never call it) and `recap/index.ts` refuses `auto: true` from anybody but our own server. When such a send needs a translation it is bought as the **account owner**, whose id comes back from `claim_recap`.
- 2026-11-19: The recap email carries the **title, date, overview, key points, decisions and action items**, and a button to open the note. Open questions are deliberately left out, because the founder's brief named those six sections; the data is there if they are ever wanted. The layout is table-based with inline styles, because email programs throw away style sheets and anything clever. Brand blue is only ever a fill (the button); links use #99CBFF, so blue words never sit on the navy.
- 2026-11-19: Every email is built in **two versions at once**, the pretty one and a plain-words one written by hand rather than stripped from the page, and a test checks that both carry the same facts. The footer is three short lines (why you got it, Turn off recaps, who sent it and where a reply goes) rather than things joined with a separator character, which the frontend-design skill names as one of the commonest tells of generated design.
- 2026-11-19: The **Turn off recaps** link needs somewhere to land, which is why the recap settings are a real page at `/recap-emails` rather than only a box inside something else. It is also reached from the Your account box at the bottom of Home, the same place the language setting ended up and for the same reason. Like the language setting, it moves into the real Settings screen in prompt 10.
- 2026-11-19: The server, not the screen, decides which row in the Send recap list is **you**: `previewRecap` adds `is_you` by comparing ids. The dialog had briefly used the signed-in email for this, which coupled it to the login context and broke the note screen's tests. Comparing ids on the server is both correct and one less thing the dialog has to know.
- 2026-11-19: Adding a fourth pill (Send recap) to the note page made the pill row wider than a phone, and the whole page scrolled sideways. The group needed `flexShrink: 1`: without it a wrapping row keeps its content width and pushes the page over. Found by looking at the screenshot, not by a test.
- 2026-11-19: `email_log` records every email Gyan **tried** to send, failures included, with the address, the language, whether it was translated, the provider's own message id, who pressed Send (empty for an automatic send) and why it failed. Anybody on the account can read it; only the server writes it. One person's email failing never stops the others.
- 2026-11-19: In a translated recap the **words of the note are translated, but the email's own headings are not**: "Key points", "Decisions", "Action items" and the "Open this note in gyan" button stay in English. This follows the rule already set on 2026-11-18 for right-to-left text, that only the translated words change and the app's own chrome stays in English. It is more arguable in an email than in the app, because the whole email is for one person and there is no English interface around it. Translating them would mean a small list of about 4 phrases in each of the 16 languages, written once; it does not need an AI call. **Open for the founder to decide**, and visible in docs/help/images/recap-email-translated-390.png.

- 2026-11-19: **Port 465, and it is the only choice.** Hostinger offers 465 (encrypted from the first byte) and 587 (starts in the clear, then turns encryption on). So this is the one part of the feature whose foundation is not documented. If Supabase ever closes 465, every send fails with "Gyan could not reach the mail service", `email_log` fills with `failed` rows saying so, and the fix is to go back to an email service that works over the web; that is a change to `index.ts` alone.
